# SAE（スパースオートエンコーダ）による「クエリ↔モーション」関係の分析：可否とボトルネック（初学者向け）

このドキュメントは、

> **SAE（Sparse AutoEncoder, スパースオートエンコーダ）を使って、
> 入力クエリ（テキスト）と生成モーションの関係を分析できるか？ ボトルネックは何か？**

という問いに対して、**この MotionMillion リポジトリの実装を前提に**、初学者向けに整理したものです。

結論を先に書くと：

> **技術的には「可能」。このコードは活性（activation）を取り出しやすく、
> しかもテキスト位置とモーション位置が系列上で分離されているため分析に向いている。**
> **ただし「SAE の学習コスト」「モーション側特徴の意味づけ（解釈）」「因果関係の特定」
> という 3 つの大きなボトルネックがある。**

---

## 1. 前提知識：SAE とは何か（超ざっくり）

ニューラルネットの内部表現（活性ベクトル）は、1 つの次元が複数の意味を同時に担う
**多義的（polysemantic）**な状態になっていて、人間には解釈しづらいです。

**SAE** は、この活性ベクトル $h$ を、

- **少数の特徴だけが発火する（スパースな）**、
- **元より次元数が多い（overcomplete な）辞書**

に分解し直すことで、**1 特徴 1 意味（monosemantic）に近い、解釈しやすい特徴**を取り出す手法です。
機械的解釈可能性（mechanistic interpretability）でよく使われます。

### SAE の数式（最小構成）

活性 $h \in \mathbb{R}^{d}$ を入力として：

$$
f = \mathrm{ReLU}(W_{enc}(h - b_{dec}) + b_{enc}) \in \mathbb{R}^{m}, \qquad m \gg d
$$
$$
\hat h = W_{dec}\, f + b_{dec}
$$
$$
\mathcal{L}_{SAE} = \underbrace{\lVert h - \hat h \rVert_2^2}_{\text{再構成}} + \lambda \underbrace{\lVert f \rVert_1}_{\text{スパース性}}
$$

| 記号 | 意味 |
|------|------|
| $h$ | 解析対象のモデル内部の活性ベクトル（例：トランスフォーマの残差ストリーム） |
| $d$ | 活性の次元数（このモデルでは 3200(3B)/4096(7B)） |
| $f$ | SAE が抽出した**スパース特徴**ベクトル |
| $m$ | 特徴の数（辞書サイズ、$d$ の数倍〜数十倍に取る） |
| $W_{enc}, W_{dec}$ | SAE のエンコーダ／デコーダ重み |
| $b_{enc}, b_{dec}$ | バイアス |
| $\lambda$ | スパース性の強さ（L1 正則化係数） |

> ポイント：SAE は**解析したいモデルとは別に、後付けで**学習する小さなネットです。
> 本体（LLAMA や FSQ）の重みは**凍結**したまま、その活性 $h$ を集めて SAE を学習します。

## 2. このプロジェクトで「クエリ↔モーション関係」を分析するとは？

本システムのデータの流れ（`docs/01` 参照）を思い出すと：

```
テキスト ─► T5-XL ─► [LLAMA: テキスト位置 + モーション位置が同じ系列] ─► モーション・トークン ─► FSQ.decode ─► 動き
```

「クエリ↔モーション関係の分析」とは、たとえば次のような問いに答えることです。

- 「**走る**」というクエリのどの内部特徴が、どのモーション・トークン（脚の動き）を引き起こすのか？
- 「**速く / ゆっくり**」のような副詞は、内部のどの特徴に符号化され、生成に効くのか？
- 複数概念を組み合わせた文（compositional）で、特徴がどう合成されるか？

SAE は、この「内部表現」を**解釈可能な特徴に分解**することで、
こうした「**テキストの意味 → 内部特徴 → モーション**」の対応を覗く道具になります。

## 3. このコードベースは分析に向いているか？（向いている点）

実装を読むと、SAE 分析にとって**有利な条件**が揃っています。

### 3.1 活性が取り出しやすい（フックを挿せる）

LLAMA 本体 `models/lit_llama/model_hf.py` の `forward` は、
`Block` を順に適用する素直な実装です（`model_hf.py:177-181`）。

```python
for block in self.transformer.h:   # ← 各ブロック出力にフックを挿せる
    x = block(x, y_mask)
x = self.transformer.ln_f(x)
logits = self.lm_head(x)
```

PyTorch の `register_forward_hook` を `transformer.h[k]` に付ければ、
**各層の残差ストリーム $x$（= SAE の入力 $h$）を簡単に収集**できます。改造もごく小さく済みます。

### 3.2 テキスト位置とモーション位置が「系列上で分離」されている ★最重要

このモデルは、テキスト埋め込みとモーション・トークンを**1 本の系列に連結**し、
**先頭 `y_mask.sum()` 個がテキスト**、それ以降がモーションになります
（`model_hf.py:159-175`、学習時はテキスト位置を `llama_proj(clip_feature)` で置換）。

つまり、**どの位置がクエリ由来でどの位置がモーション由来か、インデックスで明確に分かる**ので、

- テキスト位置の活性に SAE を当てれば「**クエリの特徴**」、
- モーション位置の活性に SAE を当てれば「**モーションの特徴**」、

と**モダリティを分けて解析**できます。これは分析にとって大きな追い風です。

### 3.3 学習データが大量にある

SAE は大量の活性サンプルを必要としますが、MotionMillion は **200 万シーケンス**あり、
活性を吐き出す元データには困りません（むしろ後述の通り「多すぎて計算が重い」方が問題）。

### 3.4 離散トークン側の足場がある

モーションは FSQ により **65536 種の離散トークン**になっています（`models/FSQ.py`）。
トークン → モーションへ戻す `forward_decoder`（`models/vqvae.py:127`）と
可視化（`inference_single.py:148-162`）が既にあるので、
「ある特徴が発火したときに、実際どんな動きが出るか」を**デコードして目視確認**する経路が用意されています。

### 3.5 分析対象になり得る「活性の場所」一覧

| 候補 | 場所 | 何が見えるか | 取り出しやすさ |
|------|------|--------------|----------------|
| LLAMA 残差ストリーム（各層） | `model_hf.py:177-181` の `x` | テキスト＋モーションの混合表現（位置で分離可） | ◎ フックで容易 |
| LLAMA テキスト位置の活性 | 同上の先頭 `y_mask.sum()` 位置 | **クエリの内部特徴** | ◎ |
| LLAMA モーション位置の活性 | 同上の残り位置 | **生成途中のモーション特徴** | ◎ |
| T5-XL のテキスト埋め込み | `train_t2m_llama.py:174-180` の `last_hidden_state` | 単語レベルの意味表現（入口） | ○ |
| FSQ エンコーダ潜在 $z$ | `models/vqvae.py:91` 周辺 | モーションの連続潜在（離散化前） | ○ |
| 注意の重み（attention map） | `model_hf.py:584` の `scaled_dot_product_attention` | テキスト→モーションの「どこを見たか」 | △ 改造要 |

## 4. 分析の進め方（想定パイプライン）

初学者がイメージしやすいよう、現実的な手順を示します。

```
STEP A. 活性の収集
   学習済み 3B/7B をロード → inference_batch.py 相当でプロンプト群を流す
   → transformer.h[k] にフックを挿し、テキスト位置/モーション位置の活性を .npy で保存

STEP B. SAE の学習
   集めた活性 h で SAE（§1 の式）を学習（本体は凍結）
   → スパース特徴 f と辞書 W_dec を得る

STEP C. 特徴の解釈（意味づけ）
   各特徴 f_j について「強く発火させるプロンプト/位置」を集め、
   - テキスト側特徴: どの単語/概念で発火するかを見る
   - モーション側特徴: その特徴方向に沿ってデコード→可視化し、どんな動きかを見る

STEP D. クエリ↔モーションの対応づけ
   テキスト側特徴とモーション側特徴の「共起・相関」、
   あるいは activation patching（特徴をオン/オフして生成変化を見る）で因果を検証
```

> SAE 自体の実装はリポジトリに**含まれていません**（新規に書く必要があります）。
> ただし SAE は数十行レベルの小さなネットなので、実装難度は高くありません。
> 難しいのは SAE そのものより、後述のボトルネック群です。

## 5. ボトルネック（ここが本題）

「可能」ではあるものの、実用上は次の壁があります。重要度順に整理します。

### 5.1 ボトルネック一覧表

| # | ボトルネック | 種別 | 深刻度 | 内容 |
|---|--------------|------|--------|------|
| B1 | **活性収集とSAE学習の計算コスト** | 計算資源 | 高 | 7B モデルで大量プロンプトを流し、層ごとに高次元活性を保存・学習する必要 |
| B2 | **モーション側特徴の意味づけが大変** | 解釈 | 高 | テキストと違い、特徴に「ラベル」がない。デコード＆目視で1つずつ意味を当てる必要 |
| B3 | **相関は分かるが「因果」は別問題** | 方法論 | 高 | SAE は特徴を出すだけ。テキスト特徴→モーションへの因果は patching 等の追加手法が要る |
| B4 | **モデル/チェックポイントが重い** | 環境 | 中 | 7B＋T5-XL＋（任意で）LLAMA3.1-8B のロードに大容量 GPU メモリが必要 |
| B5 | **クエリ表現が2か所に分散** | 構造 | 中 | クエリの意味は T5-XL と LLAMA 内 `llama_proj` 後の両方に存在。どこを見るかで結論が変わる |
| B6 | **自己回帰＋混合注意の系列依存** | 構造 | 中 | モーション活性は「それまでの生成履歴」に依存。位置・時刻で特徴が変動する |
| B7 | **離散トークン語彙が巨大（65536）** | データ | 中 | FSQ はコードブックを持たない暗黙表現。トークン単位の特徴帰着が直感的でない |
| B8 | **SAE 固有の難しさ** | 手法 | 中 | dead feature（死んだ特徴）、polysemantic 残留、$\lambda$ や $m$ のハイパラ調整、再現性 |
| B9 | **評価プロンプトが少数（126件）** | データ | 低〜中 | MotionMillion-Eval は 126 prompt。体系的な特徴検証用セットは別途用意が要る（学習データ自体は潤沢） |
| B10 | **正解（ground-truth 特徴）が無い** | 評価 | 中 | 解釈の正しさを定量評価する基準が存在しない。人手評価に依存 |

### 5.2 主要ボトルネックの掘り下げ

**B1：計算コスト**
SAE 学習には数百万〜の活性サンプルが定石です。7B モデルは 1 トークンあたり 4096 次元 × 36 層。
全部保存すると容量も帯域も大きい。現実には「数層に絞る」「サンプリングする」「3B で予備実験」
といった**規模の妥協**がほぼ必須です。

**B2：モーション側特徴の意味づけ**
テキスト特徴は「どの単語で発火するか」で意味を推測できますが、
モーション特徴は人間が見ても何を表すか分かりません。
`forward_decoder` でデコードし可視化（`inference_single.py`）して、
1 特徴ずつ「これは脚の前後運動だ」等と当てる**労働集約的な作業**になります。

**B3：相関と因果の区別**
SAE が「クエリ特徴 A と モーション特徴 B がよく一緒に光る」ことを示しても、
それは相関にすぎません。「A が B を**引き起こす**」かは、
**activation patching**（A をオン/オフして生成が変わるか）や、
**attention 解析**（`model_hf.py:584` のマスク付き注意）を組み合わせて初めて検証できます。
このモデルは**混合注意**（単語=双方向／モーション=因果, `docs/02` の 4.3 参照）なので、
クエリ→モーションの情報経路を追う設計は比較的しやすい一方、解析手続きは増えます。

**B5：クエリ表現の二重性**
クエリの意味は (1) T5-XL の出力埋め込みと、(2) それを `llama_proj` で射影し
テキスト位置に差し込んだ後の LLAMA 残差ストリーム、の両方に存在します
（`model_hf.py:63,159-175`）。「クエリの特徴」と言ったときどちらを指すかで結論が変わるため、
**解析対象の層・位置を明確に固定**することが重要です。

## 6. ボトルネックへの現実的な対処（推奨）

| ボトルネック | 緩和策 |
|--------------|--------|
| B1 計算コスト | まず **3B** モデル・**少数の層（例：中間1〜3層）**で予備実験。活性はサンプリングして保存 |
| B2 意味づけ | 自動補助として「特徴を最大発火させるトップ K プロンプト/トークン」を集計し、デコード動画を並べて目視 |
| B3 因果 | SAE と併用で **activation patching / ablation** を実施。`model_hf.py` の `forward` に介入点を追加 |
| B4 環境 | 推論は `bf16`（既定）。rewrite 用 LLAMA3.1 は分析時は外す（`--use_rewrite_model` を付けない） |
| B5 二重性 | 「T5 出力」「LLAMA 第k層テキスト位置」を別々に SAE 解析し、対応を比較 |
| B6 系列依存 | 位置（テキスト/モーション）・生成ステップごとに活性を層別収集し、混ぜない |
| B8 SAE調整 | 辞書サイズ $m$・$\lambda$ を振り、dead feature 率と再構成誤差で選定。再現のため seed 固定 |
| B9/B10 評価 | MotionMillion-Eval（`assets/infer_batch_prompt`）に加え、概念を統制した自作プロンプト集を用意 |

## 7. まとめ

- **可能か？** → **YES（技術的には実施可能）**。
  - フックで活性を取りやすく（`model_hf.py:177-181`）、
  - テキスト位置とモーション位置が系列で分離され（`model_hf.py:159-175`）、
  - トークン→動きのデコード・可視化経路（`vqvae.py:127`, `inference_single.py`）も既にある。
- **最大のボトルネックは「実装」ではなく「規模・解釈・因果」**：
  1. **B1** SAE 学習の計算コスト、
  2. **B2** モーション側特徴の意味づけ（ラベル無し・人手）、
  3. **B3** 相関 → 因果の検証（patching 等の追加手法）。
- **現実的な始め方**：3B・中間数層・テキスト位置の活性から小さく始め、
  特徴をデコード可視化で意味づけし、最後に patching で因果を確認する。

> このリポジトリには SAE 実装も活性ダンプ用スクリプトも**含まれていない**ため、
> 上記パイプライン（STEP A〜D）は新規に追加する前提です。
> ただし本体（LLAMA/FSQ）は凍結したまま後付けで解析できる構造なので、改造範囲は限定的です。
